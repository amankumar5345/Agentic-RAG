1Executive summary

Litho Agentic RAG is a guarded, multi-agent AI system for semiconductor photolithography and cleanroom operations. It answers technical questions from an approved document corpus, refuses unsafe or off-domain requests, cites the evidence it used, dispatches 3D geometry into Unreal Engine 5, and provides a reproducible harness for measuring whether any of that actually works.

The project is deliberately three systems in one repository:

This handbook therefore teaches the design and the evaluation protocol, not a score.

What is genuinely strong about this project

  • Safety is architectural, not a prompt. A guardrail node runs before routing; a retrieval budget caps tool loops; geometry sizes are validated server-side; citations are checked after generation and answers abstain when unsupported.
  • The evaluation is treated as a product. Arms isolate one design decision at a time, datasets have origins and human-review rules, results carry config and dataset hashes, and README numbers are generated from JSON rather than typed by hand.
  • Honesty is enforced in code. claim_check.py fails on unbacked numeric claims; build_readme.py renders NOT YET RUN rather than inventing results; fake Unreal latencies carry ue_mode: fake.
  • It is operable. Demo mode needs no keys; live mode degrades gracefully; a rate limiter and prompt-logging gate protect a public deployment; Docker and Cloud instructions exist.

What it is not

It is not a certified safety system, not a replacement for SOPs, not a real-time equipment controller, and not a general-purpose cleanroom benchmark. Section 28 lists the limitations in detail; those limitations are part of the engineering story, not an afterthought.

2The problem it solves

2.1 The operational reality

A semiconductor cleanroom is a document-heavy, safety-critical environment. An engineer may need the maximum permitted laser exposure for a procedure, the lockout sequence for a vacuum pump, the PPE requirement for a specific solvent, or the correct way to describe a wafer pattern to a simulation tool. That knowledge is spread across vendor manuals, regulatory guidelines, internal SOPs, academic papers and training slides. Documents are long, multi-column, figure-heavy and inconsistent in terminology.

Three failure modes are common:

  1. Search is lexical. A keyword search for “interlock” misses a passage that says “protective shut-off”. Engineers waste time and may miss the governing document.
  2. Generic chatbots hallucinate. A general model will answer confidently from parametric memory, with no provenance and no awareness of site-specific rules. In a cleanroom, a plausible but wrong procedure is worse than no answer.
  3. Knowledge does not reach action. Even a correct answer about a pattern does not draw it. Simulation, training and demonstration require the answer to become a structured command that a 3D engine can execute.

2.2 Why a multi-agent RAG system

A single retrieval-augmented prompt solves only the first layer. This project adds the layers that a real deployment needs:

RequirementMechanism
Do not engage with unsafe or off-domain inputNeMo Guardrails classifies the query before any model reasoning and returns a policy refusal or a scripted dialogue.
Route work to the right behaviourA structured-output classifier selects Safety, Maintenance, Draw or Chatbot, which shapes the orchestration context.
Ground every claimHybrid retrieval, reranking, [Cn] chunk labels, a citation rule, a validator, one repair attempt and abstention.
Prevent runaway tool useA guarded tool node enforces a maximum number of retrieval calls per question.
Turn language into action safelyspawn_geometry validates shape, size and angle; refuses to guess missing dimensions; writes an atomic JSON packet for Unreal.
Prove it worksLithoBench, nine arms, guardrail/injection/geometry suites, confidence intervals, judge agreement and CI gates.

2.3 Why Unreal Engine

Unreal is used as a spatial output device, not as a game. A cleanroom trainee can say “draw a 200 mm square” and see the geometry appear in a 3D lithography scene. The bridge is deliberately file-based and one-directional: the Python agent writes a JSON packet; Unreal polls the file on tick and renders it. This keeps the AI process and the simulation process decoupled, avoids a fragile network protocol, and lets either side restart independently.

2.4 Why the evaluation layer matters more than the demo

It is easy to build a demo that answers three curated questions. It is hard to show that an agent is better than a simpler baseline, that its safety layer reduces attack success without over-refusing benign queries, that its citations are supported, and that its geometry commands are correct. The repository therefore treats evaluation as a first-class subsystem: a labelled dataset, ablations, judge validation, statistical summaries and generated reporting.

3.2 Non-goals

  • Not a safety certification. The system can refuse and cite, but it does not replace trained judgement, site SOPs or a safety officer.
  • Not a real-time controller. There is no PLC integration, no closed-loop control of lithography equipment, and no actuation beyond writing a geometry file.
  • Not a general cleanroom benchmark. One corpus and one generator family are evaluated; conclusions do not automatically transfer.
  • Not a production multi-tenant service. Authentication, per-user isolation and durable audit storage are out of scope for this version.
  • Not a substitute for human labelling. The dataset explicitly requires human verification; the pipeline refuses to evaluate drafts.

3.3 Design principles

  1. Separate policy from reasoning. Guardrails decide whether the system should engage; the LLM decides what to say only after that decision.
  2. Least-privilege tools. The model can retrieve and draw, nothing else. Drawing has its own validation and a provenance gate in the security evaluation.
  3. Fail closed on evidence. If citations cannot be validated after one repair, the system abstains and shows the closest sources.
  4. Deterministic evaluation. Temperature zero, fixed seeds, a content-addressed cache, and hashes of the dataset, config and prompt.
  5. Demo first, live optional. A reviewer can inspect every page without keys, Ollama or Unreal, and the banner always states the mode.
  6. No secrets in the repository. .env and Streamlit secrets are ignored; only .example templates are committed.

4System at a glance

Figure 1 — Runtime context. Policy runs before reasoning; tools are limited to retrieval and geometry; Unreal is a file-bridged output device.

4.1 A request, end to end

  1. Input arrives. A typed message, a browser recording, or a WAV written by Unreal’s microphone manager. Audio is transcribed by Google Speech Recognition.
  2. The guardrail runs. NeMo returns QUERY_PASSED, a DIALOG: reply, or [RAIL_BLOCKED]. Blocked and dialogue turns short-circuit to the end of the graph.
  3. The role is chosen. A structured-output classifier assigns Safety, Maintenance, Draw or Chatbot. The role is carried in state.
  4. The orchestrator reasons. It either answers directly or emits a tool call.
  5. Retrieval. load_prompt gets chunks labelled [C1]..[Cn], formats them with document and section metadata, injects the citation rule and returns a prompt to the orchestrator.
  6. The tool budget is enforced. A guarded tool node counts retrieval calls and refuses calls beyond the configured maximum.
  7. The orchestrator synthesises. It answers from the returned context, or calls spawn_geometry when the user asked for a shape.
  8. Geometry is validated. Missing size returns needs_clarification; invalid commands return structured errors; only valid commands are written atomically to the mailbox.
  9. Unreal renders. Its blueprint polls the mailbox on tick, builds spline/mesh actors, and optionally writes unreal_ack.json so the Python side can measure true end-to-end latency.
  10. Output is post-processed. Optional Hindi translation and text-to-speech, plus a trace panel in the UI showing role, retrieval calls, chunks, citations and timings.

4.2 Two planes: runtime and evaluation

The same agent code is used for both. The evaluation runner imports the production graph builder, supplies a strict judging model and a fixed dataset, and records every output. There is no separate “demo agent” whose numbers are easier to improve. This is important in interviews: the evaluation measures the deployed graph, not a simplified replica.

PlanePurposeEntry points
RuntimeServe a user, answer or draw, show evidence.streamlit run src/ui/app.py; src/core/graph.py
